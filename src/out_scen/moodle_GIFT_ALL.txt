
$CATEGORY: $course$/SA Metasploit & Meterpreter - Scenarios (Ch.1-7)

::SA-01:: A scanner reports a server has CVE-2024-1234 with a CVSS of 9.8, and a second server with no CVEs but admins log in over plain telnet with a shared password. Which do you worry about, and why? {
    =Both - the misconfigured telnet box is at least as dangerous, and attackers often prefer misconfigs since they need no exploit and raise no alert
    ~Only the CVE box - a high CVSS always wins
    ~Only the telnet box - CVEs are never exploited
    ~Neither - no CVE means no risk
    #### Ch.1\: misconfigurations are at least as important as CVEs and are often preferred. CVE \= the bug's name, CVSS \= its 0-10 score.
}

::SA-02:: You have valid administrator credentials for a fully patched, properly configured Windows box. Can Metasploit still get you in? {
    ~No - patching blocks all Metasploit access
    =Yes - known admin creds let Metasploit give you a Meterpreter shell even on a hardened box
    ~Only if there's an unpatched CVE
    ~Only over the physical console
    #### Ch.1\: credentials beat configuration. This is the whole setup for the book.
}

::SA-03:: You land a Meterpreter session but 'getuid' shows a low-privileged user. What's true about what you can do and where you can go? {
    =What you can see depends on your process's privileges, and you can migrate from a higher-privileged process down to lower ones
    ~Meterpreter can't do recon until you're admin
    ~You can migrate from low privilege up to SYSTEM for free
    ~You automatically have SYSTEM
    #### Ch.2\: data available depends on the host process's privileges; migration goes high->low. Meterpreter lives in a process in memory, which is why file scanning misses it.
}

::SA-04:: Scenario\: your lure is a tiny buffer overflow with almost no room for code, and later you phish a laptop on flaky hotel wifi that may drop after one connection. Which payload type for each, and why? {}
// MODEL ANSWER: Tiny space -> STAGED (small stub downloads the rest). Flaky one-shot network -> STAGELESS (whole payload ships at once, needs no second connection).

::SA-05:: Your payload needs to call home through a corporate firewall that blocks inbound connections. Bind or reverse? {
    ~Either works equally
    ~Neither works through a firewall
    =Reverse - the target connects out to you (LHOST/LPORT), and outbound is usually allowed
    ~Bind - the target listens and you connect in
    #### Ch.3\: reverse beats firewalls/NAT. A handler catches the callback; run it as a job (exploit -j) in the background.
}

::SA-06:: You need to brute force one service and have limited time. The book says which targets/services are faster, and what 4 things define the attack? {}
// MODEL ANSWER: Windows is faster than Linux, and SMB is faster than SSH (Windows Wins, SMB is Speedy). The 4 features: userlist, wordlist, time, defenses (Users Want Time Delays).

::SA-07:: You phish a user and they type the WRONG password into your fake Windows prompt. What happens with phish_windows_credentials? {
    ~It accepts anything and logs the wrong password
    ~It locks the account
    =It keeps re-prompting until the credentials actually validate against the system
    ~It crashes
    #### Ch.5\: that re-prompt is why it works. You can run it from an UNPRIVILEGED session to steal the logged-on user's domain/local creds.
}

::SA-08:: You generated a payload and ran it through Metasploit encoders several times, but Defender still catches it. Why? {
    ~The payload was corrupted
    ~You didn't encode enough times
    ~Encoding only works on Linux
    =Encoders dodge bad characters, not AV - modern AV watches behavior, memory and the cloud
    #### Ch.6/7\: encoding !\= evasion. Whether malware runs depends on the target's AV; Windows ships Defender.
}

::SA-09:: You want to trojanize a real program so the victim sees normal behavior. Which tool and flags, and what does static vs dynamic analysis mean for the defender? {}
// MODEL ANSWER: msfvenom with -x <real program> -k (keep it working), plus -p payload, -f format, -o outfile. Static = examine without running (strings, hashes, Ghidra). Dynamic = run and watch (strace, gdb).

::SA-10:: You're admin on a box with Defender tamper protection ON. You can't disable Defender - what's your move for a lasting blind spot? {
    ~Disable Defender in the registry (still supported)
    =Add an exclusion - excluded paths/processes are never scanned, and admins can still add them even with tamper protection on
    ~Empty the quarantine
    ~Nothing - tamper protection stops everything
    #### Ch.7\: this is the key nuance. Quarantined threats can also be restored; registry-disable is no longer supported.
}


$CATEGORY: $course$/SB Linux for Cyber Ops - Scenarios (Ch.1-8)

::SB-01:: You get a Linux shell and want your commands left out of history, and you notice '.' is early in the user's PATH. What do these two facts give you? {
    ~Nothing useful
    ~Only history matters, PATH is harmless
    ~Only PATH matters, history can't be cleared
    =Hide tracks (unset HISTFILE / HISTSIZE\=0 / set +o history) and hijack a command by dropping a fake binary that '.' in PATH runs first
    #### Ch.1\: PATH is THE security env var; attackers also suppress bash history. A shell also behaves differently by how it's started (login vs not).
}

::SB-02:: You find a second account in /etc/passwd with UID 0, and another account whose hash in /etc/shadow starts with '!'. What does each mean? {}
// MODEL ANSWER: UID 0 = root, so that second account is a hidden root backdoor (Linux authorizes by UID, not name). '!' in front of the hash = the account is locked.

::SB-03:: You crack a hash from /etc/shadow that starts with $6$. What is it, and how did John get the password? {
    ~MD5, reversed mathematically
    ~Plaintext already
    ~bcrypt, decrypted with the salt
    =SHA-512, found by repeated guessing (hash a guess, compare) - hashes are one-way, not reversible
    #### Ch.3\: $1$\=MD5, $5$\=SHA-256, $6$\=SHA-512, $y$\=yescrypt. Salt \= same password hashes differently per account, so rainbow tables fail.
}

::SB-04:: You can edit the sshd PAM stack. How do you get a shell on every SSH login attempt, even failed ones? {
    ~Change the login shell
    =Add pam_exec.so - it runs your program during authentication regardless of success
    ~Delete /etc/shadow
    ~Add pam_pwhistory.so
    #### Ch.3\: pam_exec.so is the abuse; admins and attackers with privilege can edit PAM (/etc/pam.d).
}

::SB-05:: An attacker logged in via SSH and wiped one login record, but you still caught the login. Name the 3 record systems and why wiping one isn't enough. {}
// MODEL ANSWER: utmp (who/w/last), lastlog (pam_lastlog.so), systemd (loginctl). Different programs write each, so scrubbing one leaves the login in the others.

::SB-06:: You see a process named 'nginx' using 100% CPU but the box doesn't run a web server. How do you confirm it's really an attacker's renamed binary? {
    =Check /proc/<pid>/exe - it points at the real file on disk no matter what the process is named
    ~Reboot and see if it returns
    ~You can't - the name is authoritative
    ~Check its PID number
    #### Ch.5\: defenders hunt by name, so attackers rename; /proc/<pid>/exe defeats it. Talk to a process with signals\: SIGKILL(9) can't be caught, SIGTERM(15) can.
}

::SB-07:: An attacker wants persistence that survives reboot on a systemd box. Where do they put it, and where do you look? {
    ~Nowhere - systemd can't persist malware
    =A malicious .service unit or timer in /etc/systemd/system; check systemctl list-unit-files --state\=enabled and list-timers
    ~In /tmp only
    ~In bash history
    #### Ch.5\: systemd is PID 1; admins and attackers both use it. 
}

::SB-08:: You locked yourself out of a Linux box (lost root password) and separately find a SUID-root binary you don't recognize. What can you do with each? {}
// MODEL ANSWER: Lost password: boot rescue/install media, mount the disk, chroot in, reset with passwd. Unknown SUID-root (find / -perm -4000): runs as root, so it's a privilege-escalation path or a planted backdoor shell.

::SB-09:: A Red Hat box runs SELinux; an Ubuntu box runs AppArmor. One-line difference, and can both run at once? {
    ~Both only log, never block
    =SELinux \= labels on everything, deny-by-default, tuned with Booleans; AppArmor \= one profile per critical program; generally only one is active
    ~They're identical and always run together
    ~AppArmor labels everything; SELinux uses profiles
    #### Ch.7\: SELinux context \= user\:role\:type\:level (U aRe Totally Locked). Modes\: enforcing/permissive/disabled; aa-logprof fixes an AppArmor profile from denials.
}

::SB-10:: You're told to make sure software on a Linux fleet is trustworthy. What two things matter most? {
    ~Nothing after install
    ~Only that apt is used
    ~Only the file names
    =Repositories are valid (signed with trusted GPG keys) and installed files still match their package hashes (rpm -V, debsums)
    #### Ch.8\: apt\=Debian/Ubuntu/Mint, dnf/yum\=Red Hat/Rocky, zypper\=SUSE. Snap/Flatpak bundle dependencies (but publisher patches them, not the distro).
}


$CATEGORY: $course$/SC Windows for Cyber Ops - Scenarios (Ch.1-8)

::SC-01:: In a log you see powershell.exe launched with -EncodedCommand and a long Base64 string. What is happening, and why do attackers do it? {
    ~A normal Windows update
    =An obfuscated PowerShell command - Base64 hides keywords from simple command-line matching
    ~A corrupted command
    ~PowerShell being disabled
    #### Ch.1\: Base64 and downloaded modules are the two obfuscation methods. PowerShell is the modern shell (runs on Linux too); cmd runs a registry AutoRun at startup and keeps history.
}

::SC-02:: You get cmd.exe to open and your command runs every time - you added a value in the registry. Which, and why do attackers like it? {
    ~An environment variable
    =The Command Processor AutoRun value - quiet user-level persistence inside a trusted program
    ~The Run key only works for PowerShell
    ~A scheduled task
    #### Ch.1\: cmd executes AutoRun from the registry on startup.
}

::SC-03:: A domain group and a local group have the same name. A user is in the domain group - are they in the local group too? {
    ~Yes, same name means same group
    ~Only on domain controllers
    =No - different groups with different SIDs; domain membership doesn't grant local membership
    ~Only if they share a RID
    #### Ch.2\: SIDs identify users/groups; well-known ones (S-1-5-18\=SYSTEM, RID 500\=Administrator) are the same everywhere. Local data\=SAM, domain data\=Active Directory.
}

::SC-04:: You dumped NTLM hashes but can't crack them in time. How do you still use them, and where did they come from? {}
// MODEL ANSWER: Pass-the-hash: use the hash itself to authenticate instead of the password. They live in the SAM (local) and ntds.dit (domain); protected so even SYSTEM can't read them directly - you pull them as Administrator or Backup Operator.

::SC-05:: You download a flagged payload but want it to dodge the extra scrutiny Windows gives internet files. What do you do? {
    ~Zip it with a password only
    ~Nothing can avoid it
    ~Rename the .exe
    =Ship it inside a .iso or .vhd - those containers avoid the Mark of the Web
    #### Ch.4\: MOTW is stored in an NTFS alternate data stream (Zone.Identifier); copying to FAT32 also strips it. Windows files also have 8.3 short names and several timestamps.
}

::SC-06:: At a locked Windows login screen you press Shift 5 times and get a SYSTEM command prompt. What attack is this, what made it possible, and what defends against it? {}
// MODEL ANSWER: Sticky Keys attack: you took ownership of sethc.exe (via SeTakeOwnershipPrivilege/SeRestorePrivilege) and replaced it with cmd.exe. Windows Resource Protection defends against it.

::SC-07:: You want to see who can modify a service's files or a registry key. Which tools show the security properties/permissions? {
    ~Only Task Manager
    =icacls and Get-Acl, plus Sysinternals AccessChk/AccessEnum
    ~Only File Explorer (it's always accurate)
    ~Only regedit
    #### Ch.5\: File Explorer works but has subtle issues; SDDL \= permissions as a string. Registry keys and values are securable objects with their own DACL (Ch.6).
}

::SC-08:: You see svchost.exe whose parent process is winword.exe, not services.exe. Why is that a red flag, and what trick might hide it? {
    ~It's always normal
    ~svchost has no parent
    ~Word always launches svchost
    =svchost should be a child of services.exe - an odd parent signals injection/masquerade; attackers can spoof (obfuscate) a process's parent
    #### Ch.7\: defenders check the parent; attackers spoof it. Integrity levels (Low<Medium<High<System) drive UAC. Know the normal process tree.
}

::SC-09:: You find a service with an unquoted path 'C\:\\Program Files\\My App\\svc.exe' and you can write to C\:\\. How is this a privilege-escalation path? {
    ~Only on domain controllers
    ~Only if you're already SYSTEM
    =Windows tries C\:\\Program.exe first, so your planted binary runs as the service's account at startup
    ~It isn't exploitable
    #### Ch.8\: unquoted service paths + weak permissions \= escalation/persistence. Services run in the background via the Service Control Manager (sc, net, PsService, PowerShell); defined under HKLM\\SYSTEM\\CurrentControlSet\\Services. Accounts\: LocalSystem > NetworkService > LocalService.
}


$CATEGORY: $course$/SX Cross-Book - Big-Picture Scenarios

::SX-01:: Put a full attack in Cyber Kill Chain order using the book's tools\: msfvenom payload, phishing email, handler/Meterpreter, AV exclusion, recon. {}
// MODEL ANSWER: Recon -> Weaponize (msfvenom payload) -> Deliver (phishing) -> Exploit/Install (it runs, handler catches the callback) -> C2 (Meterpreter) -> Actions (recon, migrate, add AV exclusion to persist). Kill chain: Real Wizards Don't Exploit In Crowded Alleys.

::SX-02:: You need password hashes on both a Linux and a Windows box. Where is each, and what's the one-line difference in how users are identified? {}
// MODEL ANSWER: Linux: /etc/shadow. Windows: SAM (local) + ntds.dit (domain). Linux identifies users by UID numbers (0=root); Windows by SIDs (RID 500=Administrator).

::SX-03:: Compare the 'extra lockdown' layer and the 'background program' persistence spot on Linux vs Windows. {}
// MODEL ANSWER: Lockdown: Linux = SELinux or AppArmor; Windows = integrity levels (drive UAC). Background/persistence: Linux = systemd units/timers; Windows = services (Service Control Manager). Both used by admins and attackers.

::SX-04:: A defender asks how an attacker hides activity on each OS. Give the history/log trick for Linux vs Windows. {}
// MODEL ANSWER: Linux: clear bash history (unset HISTFILE) and know logins sit in 3 places (utmp/lastlog/systemd). Windows: cmd history dies with the session, PowerShell PSReadLine file can be deleted, and Base64 hides the command's content; logons show in event 4624 with limits.
